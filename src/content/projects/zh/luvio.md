**角色**：创始人、独立开发者，负责产品、架构、后端、数据与 AI、前端。

**状态**：已在 [luvio.cc](https://luvio.cc) 上线，支持自部署，AGPL-3.0 开源协议。约 10 万行 Python 代码，1100 多个测试。

## 问题

CRM 依赖人手动往表单里录数据，所以数据永远不全、永远过时。直接接一个大模型也不能解决问题，反而会制造新的麻烦：一个能直接写数据库的模型，迟早会用一句言之凿凿的幻觉覆盖掉正确的数据，而且没人分得清哪个字段是从哪里来的。

Luvio 的出发点正好相反：**数据应该是工作的副产品**，每一次自动修改都应该能审核、能追溯。

## 它能做什么

- **自己找线索**。驱动真实浏览器浏览 Google Maps，通过 API 读取 Reddit；由大模型给每条线索打匹配分，并附一句理由。
- **只提议，不覆盖**。每条建议都记录字段、新旧值、置信度和来源网址，由人在审核队列里批准或拒绝。
- **用自然语言查询数据**。自然语言问题经过语义层转换成只读 SQL，而不是把整张表塞进提示词。
- **写出有依据的开发信**。客户简报和邮件草稿里只能出现引用了已收集证据的事实。
- **自带模型**。通过 LiteLLM 支持约 140 家模型服务商：OpenAI、Anthropic、Bedrock、Vertex，或者本地的 Ollama / vLLM。设置页按模型、按天显示花费。

## 数据与 AI 设计

**有据可查的生成**。生成客户简报时，代码先把证据编好号（`E1`、`E2`……），模型的每一条论断都必须引用证据编号。缺少引用或编造引用的论断会被丢弃并计数；引用由代码转换成网址，而不是让模型写，所以网址不可能是幻觉出来的。

**宁可拦下的“大模型评审”**。每封要发出的草稿先过一遍规则检查，再由一个评审模型对照允许使用的事实打分。只要有不确定，就转给人处理；自动发送要求分数超过阈值。

**内置的对照实验**。一个工作区积累到 20 封获得积极回复的邮件后，会挑 3 封作为写作风格示例交给写信的模型。每个发送对象按哈希分到“示例组”或“对照组”（默认各一半），转化漏斗会比较两组效果。这个功能会自己衡量带来了多少提升，而不是想当然。

**自然语言转 SQL**。提示词由一套实体和指标的注册表构建（带 SQL 模板和变更记录），少样本示例从数据库中取，取不到时回退到数据库结构。校验器默认只放行只读查询。

**智能体记忆**。分两层：每次提示词里只放一份很省 token 的“名称加描述”索引，完整内容由 `recall_memory` 工具按需取回。每轮对话结束后，一个小模型从中提取值得长期记住的事实，先按名称去重、再按向量相似度去重（pgvector），然后按置信度分流：直接采纳，或者进入人工审核队列。

**先用便宜的规则，再用昂贵的模型**。回复分类先用规则识别退订和自动回复，剩下的才交给大模型；线索去重依次按 Google 地点 ID、名称加地点的指纹、邮箱和电话匹配。

**因果营销组合引擎（研发中）**。实现了几何衰减（adstock）、Hill 饱和曲线、结构因果模型、反事实分解和预算优化器，并用反驳检验（安慰剂处理、随机共同原因、数据子集、时间留出）做验证。已经实现并有单元测试，还没有接入产品。

## 架构

```text
           ┌──────────── frontend (web) ────────────┐
           │                                        │
   ┌───────▼────────┐                     ┌─────────▼──────────┐
   │ Go control     │  state & policy     │ Python data plane  │
   │ plane          │◀───────────────────▶│ agents · LLMs      │
   │ CRUD · auth ·  │   MCP tool gateway  │ nl2sql · memory ·  │
   │ RBAC · tenancy │                     │ sourcing · enrich  │
   │ audit · events │                     │ prospecting        │
   └───────┬────────┘                     └─────────┬──────────┘
           │        Postgres 18 + pgvector          │
           └──────────────────┬─────────────────────┘
                              │
                  desktop (Tauri): signed playbooks run
                  in the user's own logged-in browser
```

- **Go 和 Python 严格分工**。Go 负责状态和权限策略；所有调用模型的逻辑都在 Python，Python 通过 MCP 工具网关访问工作区的 API。这条规则由 CI 强制检查：Python 服务不能挂载路由归属文档里没有登记的 API 前缀。
- **每次修改都是一条事实**。对公司、联系人、商机的每一次写入，都会生成一条不可修改的字段级事件，记录是谁、通过什么途径改的。阶段历史和停留时长都从这条事件流里推算，而不是靠快照。
- **公共目录，私有管道**。`companies` 是按指纹去重的公共公司目录，带确认次数和新鲜度；`tenant_companies` 保存每个工作区自己的销售管道；`data_contributions` 记录每个字段的来源。

## 收获

让大模型参与业务流程，核心其实是**数据溯源问题**，而不是提示词问题。一旦每个值都带着来源、置信度和修改者，审核队列、审计记录和销售分析都能从同一条事件流里自然得出。

## 下一步

目前的质量控制都发生在运行时：引用检查、评审模型、按置信度分流和对照实验。下一步是为客户简报、邮件草稿和自然语言转 SQL 建一套**离线评估集**，这样换模型或改提示词之前，就能先比较效果再上线。

## 背景

Luvio 起步于 2025 年，最早叫 ProjectUp，是一个项目协作工具，做过 BM25 加向量的混合检索（倒数排名融合加重排模型），还能从团队聊天里抽取知识图谱。2026 年初它转型为数据分析和销售智能体平台，2026 年 9 月把七个仓库合并成了现在这个开源 CRM。
